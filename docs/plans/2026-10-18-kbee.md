# kbee Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build kbee, an open-source, agent-agnostic set of Agent Skills that runs a six-stage AI SDLC across multiple repos, backed by a shared, cited, self-checking knowledge base kept in its own git repo.

**Architecture:** The product is a GitHub repo of skill folders (`skills/kbee-*/SKILL.md`), installable with `npx skills add <owner>/kbee`. Rules shared by all skills (accuracy, approvals, KB layout, finding the KB) and a zero-dependency Node helper (`kbee-tool.mjs`: manifest, citations, staleness) live once in `shared/` and are copied into every skill folder by `scripts/sync-shared.mjs`, because skills.sh installs each skill folder on its own. Every skill must also work without the helper, by following the manual fallback written in its SKILL.md.

**Tech Stack:** Markdown (Agent Skills format), Node.js ≥ 18 ESM with no dependencies, `node:test`, git.

**Spec:** `docs/specs/2026-10-18-kbee-design.md`

## Global Constraints

- Skill names are `kbee-init`, `kbee-feature`, `kbee-kb`, `kbee-spec`, `kbee-plan`, `kbee-build`, `kbee-review`, `kbee-ship`, `kbee-sync`.
- `SKILL.md` frontmatter must follow Agent Skills: `name` is lowercase-hyphenated, ≤ 64 chars, and equals the folder name; `description` is non-empty and ≤ 1024 chars; the body is ≤ 500 lines.
- The only required runtime is git plus the agent. `kbee-tool.mjs` is optional: Node ≥ 18, no npm dependencies. Every SKILL.md step that uses it gives a manual fallback.
- Must work on macOS, Linux, and Windows: use `path` and `execFileSync` (never shell strings), and handle CRLF.
- Nothing organization-specific anywhere: skills, docs, examples, and fixtures use the made-up "shop" example only.
- Code citations use the format `[repo@sha:path:line]` or `[repo@sha:path:start-end]`, where `sha` is 7–40 lowercase hex characters and `path` uses forward slashes. Non-code citations use `[source: user, YYYY-MM-DD]` or `[source: <http(s) URL>]`.
- Facts about code need a code citation. Non-code sources are allowed only for decisions and the "why" behind them.
- The KB describes each repo's default branch. Feature-branch changes stay pending in `features/<slug>/` until merge.
- Approvals: bookkeeping (`features/`, manifest SHA bumps, staleness flags, `gaps.md`) is written without asking. Changes to facts (`system-map.md`, `repos/`, `contracts/`, `decisions/`) are shown and need a yes. Init gets one whole-KB approval. Pushes always need a yes.
- `kbee-feature` pauses for approval after Spec and after Plan, and otherwise only before push or opening PRs.
- If the agent supports subagents with model choice, it scans on a fast tier and synthesizes on a strong tier. Otherwise it runs everything one after another on the current model.
- v1 limits: up to about 10 repos of up to about 100k lines each. A monorepo package counts as its own repo entry. The KB is summary-level by default.
- MIT license. Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **A repo listed in the manifest isn't on this machine, or its path hint is wrong.** Expect a clear `REPO_NOT_FOUND` naming the repo and the paths tried, and `stale` reporting `missing` rather than crashing. Tests: Task 1, Task 3.
2. **A cited SHA isn't present locally** (shallow clone, or history rewritten by a force-push). Expect `SHA_NOT_FOUND` from validation, and `stale` treating the repo as stale with every citation of it affected. Tests: Task 2, Task 3.
3. **Offline, or no `origin` remote.** Expect `stale` to fall back to the local default branch with `fetchFailed: true` and not throw. Test: Task 3.
4. **A cited file was deleted or renamed after sync.** Expect the KB files citing it to show up in `affectedKbFiles`. Test: Task 3.
5. **CRLF line endings, or a hand-edited manifest with broken JSON.** Expect line counts to stay correct, and `MANIFEST_INVALID` with the parse message. Tests: Task 1, Task 2.

### Task 1: Scaffold + manifest, resolve, find

**Files:**
- Create: `package.json`, `LICENSE`, `.gitignore`, `shared/scripts/kbee-tool.mjs`, `tests/helpers/fixture-repos.mjs`, `tests/kbee-tool.manifest.test.mjs`

**Interfaces:**
- Produces (exported from `shared/scripts/kbee-tool.mjs`):
  - `class KbeeError extends Error { code: string }`
  - `loadManifest(kbDir: string): Manifest`, which throws `MANIFEST_MISSING` or `MANIFEST_INVALID`
  - `validateManifest(obj: unknown): string[]`, which returns error messages (empty means valid)
  - `resolveRepo(kbDir: string, name: string): string`, which returns an absolute path and throws `REPO_UNKNOWN` or `REPO_NOT_FOUND`
  - `findKb(startDir: string): string | null`
  - `git(cwd: string, args: string[]): string`, a trimmed stdout wrapper around `execFileSync('git', …)`
  - `Manifest = { kbeeVersion: 1, mode: 'direct'|'pr', repos: Array<{ name, url, defaultBranch, pathHint, syncedSha: string|null, syncedAt: string|null }> }`
  - CLI: `node kbee-tool.mjs <command> [args]` prints JSON to stdout. On a `KbeeError` it prints `{"error":{"code","message"}}` and exits 1. Commands in this task: `find [dir]` and `resolve <kbDir> <repo>`.
- Produces (`tests/helpers/fixture-repos.mjs`): `makeWorkspace(): Promise<{ root, kbDir, repos: Record<'shop-api'|'shop-web'|'shop-types', { dir, origin, sha }> }>`. It copies each `examples/fixtures/<name>` into a temp dir, runs `git init -b main` and commits, creates a bare `origin` clone and adds it as a remote, and creates an empty `<root>/shop-kb` with a valid manifest whose `pathHint`s are `../<name>` and whose `syncedSha` values are the initial commits. The fixture dirs are created in Task 5. Until then, the helper may create a single placeholder file per repo when the fixture dir is absent.
